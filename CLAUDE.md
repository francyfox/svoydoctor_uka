## Directus — модель контента

**Перед любой правкой схемы Directus (поля/коллекции/связи/группировка полей) сначала загрузи skill `directus`** (`.claude/skills/directus/SKILL.md`) — там задокументированы конкретные баги `mcp__directus__*`-инструментов на этом инстансе (роняют `special`, неверный параметр у `create-item`, `update-item` не работает на singleton-коллекциях) и рабочий рецепт группировки полей (tabs/group-raw/group-detail, включая обязательный `special: ["alias","no-data","group"]` — без него группа пропадает из листинга полей).

- Один инстанс, без staging: `https://directus-11-17-4.onrender.com` (Render + Neon Postgres + R2). Все схемные изменения через MCP/API идут сразу в прод.
- Контент организован как singleton-коллекции (`settings`, `section_hero`, `section_services`, `section_symptoms`, `section_we_help`) с O2M в `*_translations` (по одной строке на локаль `ru`/`kk`).
- Повторяющиеся элементы внутри секции — НЕ JSON-репитеры, а отдельные дочерние коллекции (напр. `section_hero_block`, `section_hero_advantage`, `section_services_item`, `section_symptom`, `section_we_help_item`), связанные O2M с соответствующей `*_translations`. Раньше это были JSON-поля (`advantages`, `items`, `symptoms`) — их конвертировали в коллекции 2026-08-06, т.к. репитеры неудобно редактировать.
- Паттерн дочерней коллекции: скрытое поле `sort` (integer, порядок drag-n-drop) + скрытое `ref_id` (integer FK → `<parent>_translations.id`, `on_delete: SET NULL`), на родителе — alias-поле того же имени (`special: ["o2m"]`, `interface: "list-o2m"`) с `relation.meta.sort_field: "sort"`.
- MCP-инструменты `mcp__directus__*` НЕ включают создание/удаление коллекций, полей-связей (relations) — для этого нужны прямые REST-вызовы (`curl` к `$DIRECTUS_URL` с `Authorization: Bearer $DIRECTUS_TOKEN` из `.env`): `POST /collections`, `POST /relations`, `DELETE /fields/:collection/:field`.
- Маппинг Directus-строк → типы приложения (`src/lib/types/content.ts`) живёт в одном месте — `src/lib/server/directus.ts`. При правках схемы менять нужно только его; вниз по стеку (`+server.ts`, `queries/*.ts`, компоненты) ничего трогать не надо, пока форма `Settings`/`Section*` не меняется.

## Изображения, видео и иконки из Directus

- `src/components/ui/image/image.svelte` (`Image`) — компонент для растровых фото из Directus (лого, фото клиники, иллюстрации услуг, фото блока "мы помогаем", фон hero-тайла). Использует `@unpic/svelte` (`cdn="directus"`) + Directus on-the-fly transform API (`/assets/:id?width=&format=&fit=`, публично доступен без токена). Пропсы: `id` (UUID файла или `undefined`), `width`/`height`, `fit`, `priority` (для контента над сгибом — лого, первый hero-тайл). **Если `id` не передан — сам рисует нейтральный визуальный плейсхолдер (иконка, без текста)**; вызывающему компоненту НЕ нужно писать свой `{:else}` с текстом типа "фото клиники" — просто рендерить `<Image>` безусловно.
- `src/components/ui/video/video.svelte` (`Video`) — фоновое видео из Directus (напр. hero-тайл), автоплей+луп+mute+playsinline по умолчанию (обязательно для автоплея в браузерах), тот же паттерн skeleton/error, что и у `Image`. Directus не трансформирует не-картиночные файлы — `src` строится через `buildAssetUrl(id)` без параметров.
- `src/components/ui/directus-icon/icon.svelte` (экспортируется как `Icon` из `ui/directus-icon/index.ts` — не путать с `ui/icon/icon.svelte`, который тоже `Icon`, но для статичных app-иконок типа whatsapp/instagram; при коллизии импортов алиасить на месте) — для SVG-иконок (напр. `HeroAdvantage.iconId`), без format-negotiation, через `src/lib/directus/assets.ts` (`buildAssetUrl`).
- Типы в `content.ts` хранят **id файла** (`logoId`, `illustrationId`, ...), а не готовый URL — компонент сам строит нужные варианты (ширины/форматы). Собирает и мапит их `src/lib/server/directus.ts`.
- `HeroBlock.background: { id, kind: 'image'|'video' } | undefined` — `kind` определяется по mime-типу файла (`media.type` из `directus_files`, начинается с `video/` → video). `hero-tile-media.svelte` рендерит `Image` или `Video` в зависимости от `kind`, и если у тайла есть `title`/`description` — рисует тёмный градиент (`bg-gradient-to-t from-black/70`) поверх медиа для читаемости текста. `hero-tile-title.svelte`/`hero-tile-promo.svelte` умеют то же самое (опциональный `background`/`backgroundId` проп) — если фона нет, остаются сплошным цветом (`bg-primary`/`bg-accent`) как раньше.
- `section_hero_block` изначально (до 2026-08-06) был не O2M, а фактический O2O — `ref_id` имел `is_unique: true`, из-за чего на перевод помещался только ОДИН блок. Позиции тайлов в `hero.svelte` строго позиционные (`[title, photo, promo, description, media] = blocks`, сортировка по полю `sort`) — чтобы дотянуться до 5-й позиции (media-тайл под иконками), нужны все 5 блоков по порядку, даже если 4-й (`description`) нигде не рендерится (заполняй service-заглушкой, не оставляй дыру в sort). Не путай эту позиционную модель с UI-ready O2M-коллекциями остальных секций — здесь редактирование через Directus admin потребует знания, что четвёртая карточка технически "мёртвая".
- Above-the-fold картинки/видео ОБЯЗАТЕЛЬНО с `priority` (иначе `loading="lazy"` — в связке с окружением `claude-in-chrome` это часто вообще не грузится, см. ниже). Забыл `priority` на `hero-tile-title`/`hero-tile-promo` при их создании — картинка застревала на `naturalWidth: 0` даже в реальном браузере, не только в автоматизации.
- Тестировать автоплей видео через `claude-in-chrome` не получится — в этом окружении `<video>` не проигрывает вообще ничего (даже публичный тестовый mp4 зависает на `readyState: 0`), это ограничение браузерной автоматизации, а не баг компонента. Проверяй атрибуты (`autoplay`/`muted`/`loop`/`playsinline` на элементе) через JS-инспекцию DOM, не жди реального воспроизведения в скриншотах.

**Грабли `@unpic/svelte` 1.0.1 (учтено в реализации, не наступай снова):**
1. `<Image cdn="directus" operations={{...}}>` — `operations` ОБЯЗАН быть объектом, ключ по имени CDN: `{ directus: { format: 'auto', fit: 'cover' } }`, а не плоский `{ format: 'auto' }` — иначе тихо отбрасывается (`operations?.[cdn]` в `@unpic/core`).
2. `<Image>` не годится для format-негоциации (avif/webp): её собственный `srcset`-билдер передаёт `format: undefined` поверх `operations.format` (баг порядка spread в `@unpic/core/getSrcSet`) — реальный запрос никогда не получает `format`. Рабочий вариант — ручной `<picture>` с явными `<Source type="image/avif">` / `<Source type="image/webp">` + `<Image>` как fallback (так и сделано в `image.svelte`).
3. `<Image>` не прокидывает `onload`/`onerror` на реальный `<img>` (описаны в типах, но реально не долетают) и её `class`-проп схватывается один раз при монтировании (не реактивно) — поэтому: (a) состояние загрузки/ошибки отслеживается вручную через `{@attach}` на обёртке (`container.querySelector('img')` + `addEventListener`, плюс проверка `img.complete` на случай, когда SSR-рендеренная картинка уже догрузилась до гидратации); (b) fade-переход по `loaded` навешан на СВОЙ `<div>`-обёртку, а не как `class` на `<Image>`.
4. Directus: без явного `format=auto` в query отдаёт оригинальный формат независимо от `Accept`-заголовка — параметр обязателен для негоциации, само его отсутствие не включает её.

## Градиентный фон сайта и GLSL-фон шапки (2026-08-09)

- Сайтовый градиент — не `background-attachment: fixed` на `body` (тормозит скролл в мобильном Safari), а `body::before { position: fixed; inset: 0; z-index: -1; }` с радиальными градиентами на брендовых токенах (`src/routes/layout.css`). `position: fixed` сам по себе дешёвый композитный слой, не перерисовывается при скролле.
- Анимированный фон шапки — свой WebGL1 (без библиотек) в `src/lib/webgl/` + `src/components/ui/shader-background/shader-background.svelte`, шейдеры — реальные `.glsl`-файлы, импортируются через Vite `?raw` (`quad.vert.glsl`, `scenes.frag.glsl` в `src/lib/webgl/shaders/`). Три сцены ("аура", "поток", "клетки" — по мотивам `docs/moodboard.md`) смешиваются в одном скомпилированном шейдере через `uScroll` (0..1, прогресс всей страницы) — не пересобираем программу на секцию, дешевле на мобильных.
- Инициализация вебгл — через `{@attach}` на `<canvas>`, а не `bind:this` + `$effect` (так же, как `image.svelte` уже делает для состояния загрузки — паттерн проекта для императивной работы с DOM-узлом).
- Тип для attachment — `import type { Attachment } from 'svelte/attachments'` (МНОЖЕСТВЕННОЕ число в пути модуля). `svelte/attachment` (единственное) не существует и падает молча только на `svelte-check`, не на рантайме/автофиксере.
- Перф на мобильных: внутреннее разрешение канваса × 0.55 от отображаемого (мягкая абстрактная картинка не требует резкости), DPR зажат до 1.5, рендер троттлится до ~30fps, пауза через `document.hidden` и `IntersectionObserver`, `prefers-reduced-motion: reduce` — один статичный кадр без `requestAnimationFrame`.
- Отладка через `gl.readPixels` "снаружи" (например, из devtools-скрипта, не в момент отрисовки) может вернуть `[0,0,0,0]` даже когда шейдер рендерит правильно — с `preserveDrawingBuffer: false` (наш случай, дефолт) буфер может быть уже очищен браузером между кадрами compositing. Для проверки нужно дёргать `gl.drawArrays` + `gl.readPixels` синхронно в одном вызове, не полагаясь на буфер между независимыми rAF-кадрами.
- Плитка шапки поверх канваса — полупрозрачная заливка `bg-background/30` + `backdrop-blur-sm`, не сильнее: на `/45` + `blur-md` шейдер практически не виден за подложкой (проверено визуально, `/75` из первой попытки — вообще белый прямоугольник).
- `min-h-dvh` на каждую секцию — но НЕ через `h-full`-цепочку у детей (`section` с `min-height` не даёт вложенным `%`/`fr`-трекам определённой высоты — CSS-грид/проценты внутри резолвятся в `auto`, ломая раскладку). Рабочий паттерн: `section` = `flex flex-col min-h-dvh`, прямые дети = `flex-1` вместо `h-full` — flexbox даёт им определённую высоту независимо от того, откуда она у родителя (контент или `min-height`). Так сделано в `hero.svelte` (сетка тайлов внутри). Для секций без внутренней процентной раскладки (`services`/`symptoms`/`we-help`/`contacts`) достаточно `flex min-h-dvh flex-col justify-center` на самой `section` — контент центрируется по вертикали, если короче экрана.
- `resize_window` через `claude-in-chrome` не работает надёжно в этом окружении (тайловый WM на Manjaro игнорирует программный ресайз) — для проверки мобильной раскладки полагайся на код-ревью самих `dvh`/flex-паттернов и на пиксельную проверку через `gl.readPixels`/`getBoundingClientRect`, а не на скриншот в узком вьюпорте.
- То же окружение иногда помечает MCP-вкладку как `document.hidden === true` / `visibilityState: "hidden"` (при этом `document.hasFocus()` — `true`) — судя по всему, окно физически не отображается поверх других из-за тайлового WM. В этом состоянии зависают `Page.captureScreenshot` и колбэки `IntersectionObserver` (rAF при этом ещё срабатывает). Это не баг компонента — пауза рендера по `document.hidden` в `ShaderBackground` отрабатывает штатно. Если скриншоты/JS с `await`-ожиданием рендер-зависимых колбэков массово подвисают — сначала проверь `document.hidden` через синхронный `javascript_tool`, а не считай это зависанием страницы.

## Фоны отдельных секций — по одной GLSL-сцене на секцию (2026-08-10)

- Изначально фон на GLSL повесили только на шапку; по фидбеку пользователя — ожидались отдельные "картины" (по мотивам мудборда) в каждой секции, а не только блендинг в шапке. Теперь у каждой секции своя сцена: hero=`aura.frag.glsl` (аура бренда), services=`flow.frag.glsl` (структурированный поток), symptoms=`cells.frag.glsl` (взаимодействие микро-клеток, подмешан `--color-success` — единственный шейдер с этим юниформом), we-help=`mosaic.frag.glsl` (клеточная мозаика — сетка hash-based пульсирующих кружков, дешевле metaball-луп), contacts=`spectrum.frag.glsl` (баланс спектра). Шапка держит отдельный смешанный `scenes.frag.glsl` (три сцены блендятся по прогрессу скролла всей страницы) — она одна на весь сайт и всегда видна, поэтому оправданно показывает "путешествие" по мотивам, пока остальные секции показывают каждая свой один.
- `ShaderBackground` принимает `fragment` (raw-исходник шейдера, а не захардкоженный импорт) и `mode: 'page' | 'local'` (дефолт `'local'`). `page` — прогресс скролла всей страницы (шапка). `local` — `uScroll` считается по самому элементу (`(vh - rect.top) / (vh + rect.height)`, 0 при входе снизу, 1 при выходе сверху).
- В каждом шейдере — общий "envelope" `smoothstep(0,0.18,uScroll) * smoothstep(1,0.8,uScroll)`, который плавно проявляет/скрывает сцену на входе/выходе секции из вьюпорта — это и есть ответ на "взаимодействие со скролом" для секционных фонов (в отличие от шапки, где скролл двигает блендинг сцен, а не альфу).
- Неиспользуемый в конкретном шейдере uniform (например `uSuccess` в `flow`/`aura`) даёт `gl.getUniformLocation → null` — присваивать ему значение всё равно можно, WebGL-спека такое присваивание молча игнорирует; не нужно писать `if (uSuccess) ...` на каждый юниформ.
- `prefers-reduced-motion`: без rAF-цикла статичный кадр всё равно должен обновляться при смене `uScroll` (иначе секция ниже сгиба навсегда останется невидимой — never получит свой единственный кадр с ненулевой альфой) — поэтому `onScroll` дергает `renderStatic()` отдельно, не полагаясь на цикл `draw()`.

### Три реальных бага в первой версии (2026-08-10, найдены по репорту пользователя "ничего не отображается")

1. **WebGL-контекст нельзя пересоздавать через IntersectionObserver.** Первая версия секционного `ShaderBackground` создавала/уничтожала (`WEBGL_lose_context().loseContext()`) контекст при каждом входе/выходе секции из вьюпорта, думая, что это дешевле, чем 6 постоянно живых контекстов. На практике частый create/destroy быстро упирается в лимит браузера на число живых WebGL-контекстов и роняет их — пользователь увидел нативное `"WebGL context was lost"`. Правильный паттерн: контекст создаётся один раз при `{@attach}` и живёт всё время, пока канвас смонтирован; `IntersectionObserver`/`document.hidden` управляют только тем, крутится ли rAF-цикл (`gl.clear`+`drawArrays`), а не жизненным циклом самого контекста. Дополнительно обязательны `webglcontextlost`/`webglcontextrestored`-обработчики на канвасе (`event.preventDefault()` на lost, чтобы контекст мог восстановиться, пересоздание program/uniform'ов на restored) — драйвер/браузер может уронить контекст и без нашего участия (смена вкладки, GPU-reset на мобильных).
2. **`-z-10` на канвасе внутри секции без своего stacking context — контент невидим/неуправляем.** `position: relative` на `<section>` САМО ПО СЕБЕ не создаёт новый stacking context (нужен ещё явный `z-index`, не `auto`) — поэтому `-z-10` на дочернем канвасе "убегает" из секции к ближайшему реальному stacking context (фактически к корню документа) и там конкурирует по z-index со всеми остальными элементами страницы, а не только с соседями внутри своей секции. Итог непредсказуем и на практике даёт невидимый фон. Рабочий паттерн — тот, что уже был в шапке: НЕ ставить z-index вообще, просто класть канвас первым ребёнком секции, а следующий за ним контент-контейнер — с `relative` (оба тогда оказываются "positioned, z-index:auto" — красятся в порядке DOM, контент поверх канваса). Если действительно нужен явный z-index — сначала дать самой секции `isolate` (создаёт новый stacking context без побочных эффектов z-index), иначе он не будет локальным.
3. **Имя локальной переменной `dot` в `mosaic.frag.glsl` совпадало со встроенной функцией `dot()`.** Легально в части GLSL ES 1.0 реализаций, но не на всех драйверах/компиляторах — переименовано в `d`. Общий урок: не называть переменные как built-in функции GLSL (`dot`, `mix`, `length`, `reflect`, ...), даже если локальный компилятор это проглатывает.
4. **Самый вероятный настоящий виновник "ничего не видно" на реальной машине пользователя: `smoothstep(1.0, 0.8, uScroll)` — края в обратном порядке (`edge0 > edge1`).** По спецификации GLSL это undefined behavior. На Mesa/SwiftShader (окружение агента) драйвер трактует это "прощающе" через прямую формулу `t=clamp((x-edge0)/(edge1-edge0),0,1)` и математически (деление отрицательного на отрицательное) СЛУЧАЙНО даёт почти верный результат — из-за этого локальная принудительная отрисовка через `gl.readPixels` показывала корректную картинку, маскируя баг. На другом драйвере (ANGLE/Windows, другой GPU) UB вполне может дать всегда `0` — то есть альфа-канал везде ноль, фон невидим целиком, при том что шейдер успешно компилируется и линкуется (никакой ошибки в консоли). Исправлено на портируемую форму `1.0 - smoothstep(0.8, 1.0, uScroll)`. Урок: **никогда не проверять GLSL-логику только на одном рендерере** — компиляция без ошибок ничего не говорит о корректности UB-конструкций; если поведение шейдера отличается от ожидаемого только у пользователя — в первую очередь подозревай UB (обратные edge0/edge1 в `smoothstep`/`clamp`-подобных функциях, деление на ноль в погранично-нулевых случаях), а не "не должно быть видно только у меня".
5. **Раздельная HMR-ловушка:** правки `.glsl`-файлов (импортируются через `?raw`) не всегда триггерят Vite HMR-обновление у уже открытой страницы (в этой сессии HMR-лог ни разу не показал `hot updated: .../*.glsl` даже после правок) — при этом прямой `curl`/новый `import()` уже отдают свежее содержимое, т.е. сам dev-сервер обновлён корректно, просто открытая вкладка может держать старый скомпилированный шейдер в памяти. После правки `.glsl`-файла всегда проси **полный reload вкладки** (не полагайся на HMR), прежде чем делать вывод о том, что фикс не сработал.

Смежный урок по верификации: `svelte-check`/`svelte-autofixer` проверяют только TS/Svelte-код, не содержимое `.glsl`-строк — компиляцию шейдера они не ловят. Чтобы проверить реальную компиляцию GLSL без зависимости от рендера страницы (полезно, когда `document.hidden` мешает скриншотам/`IntersectionObserver`, см. выше), собери шейдер в offscreen-канвасе через `javascript_tool` (создать `<canvas>` вручную, `getContext('webgl')`, скомпилировать/слинковать программу, `gl.readPixels` сразу после `drawArrays` в том же вызове) — это synchronous и не зависит от compositing/paint pipeline, в отличие от скриншота.

Заменено на `h-[70dvh]` (жёсткая высота) + `overflow-hidden` на `.accordion-strip-content` — контент, который не влезает, обрезается, а не раздвигает контейнер. Общий урок: `min-h-*` на контейнере с ДИНАМИЧЕСКИ меняющимся контентом (аккордеон, таб-панель) почти всегда даёт скачки лейаута — если контейнер не должен менять размер между состояниями, нужен `h-*`, а не `min-h-*`, с обрезкой лишнего через `overflow-hidden` на внутреннем блоке.
- **Респонсив аккордеона услуг** (`services.svelte`): при большом числе табов (6) на узких экранах закрытые вкладки (по 60px каждая) съедают слишком много ширины, не оставляя места под открытую панель — решение: снипет `content` вынесен на верхний уровень компонента (`{#snippet content(item)}` вне `{#if}`/секции) и переиспользуется в ДВУХ структурах через `{content}`-шоткат: `<div class="flex flex-col gap-4 lg:hidden">` с двумя независимыми `<AccordionStrip>` (по половине услуг каждый) и `<div class="hidden lg:flex">` с одним аккордеоном на все услуги — переключение чисто CSS-классами (`lg:hidden`/`hidden lg:flex`), оба варианta присутствуют в DOM всегда (SSR-safe, никакого hydration mismatch от JS-детекции брейкпоинта).
- Активный/неактивный таб и hover — через `opacity-100` (открыт) vs `opacity-75 hover:opacity-100` (закрыт) + `hover:brightness-110` на самой кнопке, в одном `transition-[flex,opacity,filter] duration-500` — три анимируемых свойства в одном списке, не три отдельных transition-правила, иначе таймínги легко рассинхронятся. При проверке через `getComputedStyle().opacity` сразу после программного клика (без ожидания конца transition) значение может быть ещё старым/промежуточным — сверяйся с реальным списком классов элемента (`element.className`), а не с computed style, если проверяешь ДО завершения transition-duration.
- **Два реальных бага при доводке "дверной" анимации аккордеона (2026-08-10):**
  1. Контент закрываемой панели раньше рендерился через `{#if isOpen}` — Svelte **мгновенно** убирает узел из DOM на false (никакого transition на unmount), поэтому пока обёртка ещё 700мс визуально сжималась, внутри уже было пусто — рваный эффект. Фикс — контент всех вкладок теперь смонтирован ВСЕГДА (без `{#if}`), видимость только через ширину обёртки + `overflow-hidden`. Из-за этого закрытые панели остаются в DOM и доступны скринридерам/клавиатурной навигации несмотря на визуальное сжатие до 60px — это сознательный выбор (не добавляли `inert`/`aria-hidden`), а не забытая a11y-дыра.
  2. После (1) у закрытых вкладок пропала фиксация ширины: `flex-basis: auto` (дефолт, когда на обёртке нет `flex-*` класса) в паре с всегда-смонтированным контентом внутри стал учитывать ЕСТЕСТВЕННУЮ ширину контента (текст/картинка/кнопка), а не только кнопку-таб — закрытые вкладки "распухали" непредсказуемо. Попытка форсировать `w-[60px] flex-none` тоже не подошла: `flex-none` = `flex: 0 0 auto`, то есть `flex-basis: auto` — а CSS **не умеет** плавно интерполировать `flex-basis` между `auto` (не-числовое ключевое слово) и `0%` (числовое) у открытой вкладки — transition просто пропадал, скачок мгновенный. Рабочий фикс — `flex-[0_0_60px]` (явный ЧИСЛОВОЙ `flex-basis: 60px` вместо `auto`) у закрытых: оба конца transition теперь `<length-percentage>` (`60px` ↔ `0%`), браузер интерполирует нормально. Общий урок: если `transition`/`animate` на CSS-свойстве "не работает" без единой ошибки — в первую очередь проверяй, не является ли ОДНО из двух состояний non-numeric keyword'ом (`auto`, `none`, `normal`, ...) — такие пары просто не анимируются, browser молча делает мгновенный jump cut.

## Адаптивный AccordionStrip: 3 брейкпоинта, `mode="vertical"` (2026-08-10)

- На узких экранах (<640px) горизонтальная лента табов (`w-[60px]` каждый) физически не помещается вместе с раскрытой панелью — добавлен `mode?: 'horizontal' | 'vertical'` проп в `accordion-strip.svelte`. `vertical` — обычный аккордеон: горизонтальные полосы-табы друг под другом, раскрытие вниз, а не вбок.
- Переключение между 3 версиями (`mode="vertical"` <640px, 2 горизонтальных по половине услуг 640–1024px, 1 горизонтальный на все услуги 1024px+) — **чисто CSS** (`sm:hidden` / `hidden sm:flex lg:hidden` / `hidden lg:flex`), все 3 варианта одновременно в DOM. Обсуждали JS `matchMedia`-based реактивное определение брейкпоинта (руны это умеют — `runed` не имеет готового `MediaQuery`-хелпера, но пара строк `$state`+`$effect`+`matchMedia` решают) — в итоге не понадобилось: чистый CSS проще, SSR-safe по умолчанию (без hydration-мисматча от JS-детекции ширины при первом рендере), и это тот же паттерн, что уже работал для 2-рядной раскладки.
- Раскрытие `vertical`-режима — CSS grid-trick `grid-template-rows: 0fr → 1fr` (не JS-измерение `scrollHeight`, не `max-height`-с-подобранным-числом) — единственный no-JS способ анимировать высоту к `auto`-подобному значению для контента переменной длины.
- **Утечка контента при `grid-rows-[0fr]`:** свёрнутая панель показывала кусок картинки (было видно ~256px вместо 0) — `0fr`-трек в CSS Grid по спецификации сайзится как `minmax(auto, 0fr)`, а НЕ буквально `minmax(0, 0fr)`: браузер всё равно считает auto-минимум трека по min-content потомков. `overflow: hidden` на самой grid-обёртке НЕ убирает эту auto-минимальную высоту, если у ВНУТРЕННЕГО контентного блока (на следующем уровне вложенности) overflow остаётся `visible` — картинка с жёстким `!h-[256px]` продолжает "тянуть" auto-минимум вверх. Фикс — `overflow: hidden` должен стоять на КАЖДОМ уровне цепочки до элемента с фиксированной высотой, не только на самом grid-контейнере: добавлен `overflow-hidden` на `.accordion-strip-content` (на уровень глубже). Общий урок: `overflow:hidden` "лечит" auto-минимум только для БЛИЖАЙШЕГО потомка с этим свойством — если между grid-контейнером и проблемным фиксированным-по-высоте элементом есть промежуточный `overflow: visible` блок, он "пробрасывает" реальный min-content наверх мимо клиппинга.
- Даже с `grid-rows-[0fr]` и полным overflow-clipping'ом трека, `padding` на внутреннем контентном блоке (`p-4`) всё ещё даёт видимый просвет (32px = 16px×2) — паддинг-бокс не схлопывается вместе с высотой контента. Если нужно 0px именно у закрытой панели — паддинг тоже должен переключаться по `isOpen` (`isOpen ? 'p-4' : 'p-0'`), а не быть константой.

- Установка нового npm-пакета (`bun add @splidejs/svelte-splide`) **пока dev-сервер уже был запущен** — сайт упал в 500 "Internal Error" при первом же SSR-запросе после следующего изменения кода, без единой ошибки в консоли браузера (ошибка серверная, а браузерная консоль её не видит) и без полезной информации в самом HTTP-ответе (SvelteKit в dev режиме тоже урезает сообщение до generic "Internal Error" на клиенте — полный стек уходит только в stdout процесса, а не в HTTP body).
- Диагностика: если у dev-сервера нет доступа к его stdout (запущен не тобой, привязан к чужому pts), не гадай — подними ОТДЕЛЬНЫЙ инстанс через `vite.createServer({ server: { middlewareMode: true }, appType: 'custom' })` программно (Node-скрипт) и вызови `server.ssrLoadModule(...)` / `render()` из `svelte/server` на подозрительных компонентах напрямую — это даёт полный вывод ошибки в твоём собственном stdout, не трогая чужой процесс. Если изолированный рендер компонентов проходит чисто (как здесь) — подозревай не код, а состояние самого запущенного сервера.
- Корень проблемы: Vite дооптимизирует зависимости (`node_modules/.vite/deps`) при старте или по требованию, но уже работающий процесс не подхватывает новый пакет, добавленный в `node_modules` уже ПОСЛЕ его старта, даже если lockfile поменялся — на диске кэш может обновиться (если что-то другое, например твой диагностический скрипт, откроет свой vite-сервер и вызовет реоптимизацию), но уже подключённые клиенты у ЖИВОГО процесса всё равно держат старые ссылки на pre-bundled чанки в памяти. Просто обновлённого кэша на диске недостаточно — нужен рестарт самого процесса.
- Правило: **после любого изменения зависимостей (`bun add`/`remove`/lockfile) во время работающего dev-сервера — перезапускай его**, не полагайся на автоматическое обнаружение. Если сервер запущен не тобой (принадлежит пользователю), явно предупреди и перезапусти сам, а не трать время на угадывание причины 500-ошибки без стека.

## Порядок и видимость секций из Directus (2026-08-12)

- Новая коллекция `page_sections` (обычная, НЕ singleton — 5 строк, по одной на секцию главной страницы): `sort` (drag-n-drop, `meta.sort_field: "sort"` на самой коллекции), `section_key` (select-dropdown с фиксированными значениями `hero`/`services`/`symptoms`/`we_help`/`contacts` — намеренно закрытый список, а не свободный текст, т.к. код всё равно знает только эти 5 ключей), `visible` (boolean). Создана через `POST /collections` с полями прямо в теле запроса (Directus поддерживает создание коллекции+полей одним вызовом) — не через MCP (не умеет коллекции).
- `getPageSections()` в `directus.ts` — `readItems('page_sections', { fields: ['section_key','visible'], sort: ['sort'] })`. Важная деталь для типов Directus SDK: `sort: ['sort']` требует, чтобы поле `sort` присутствовало в TS-типе строки коллекции (`PageSectionRow`), ДАЖЕ если оно не запрошено в `fields` — SDK валидирует допустимые значения `sort` по полному типу строки в `Schema`, не по фактически выбранным полям. Забыл это при первой версии — `tsc` сразу отловил (`Type '"sort"' is not assignable to...`).
- `+page.svelte` был переписан с жёсткой последовательности `{#if heroQuery.data}<Hero/>{/if}{#if servicesQuery.data}...` на `{#each visibleSections as section (section.key)}{#if section.key === 'hero'}...{:else if ...}{/if}{/each}`, где `visibleSections = pageSectionsQuery.data.filter(s => s.visible)` — порядок и факт присутствия секции теперь полностью определяются данными из Directus, в коде нет захардкоженного индекса/последовательности. Добавление НОВОЙ секции (не одной из существующих 5) всё ещё требует правки кода (нового `:else if`-бренча + компонента) — это не "no-code" в абсолютном смысле, а именно то, что просил пункт 2 (`docs/need.md`): реордер/скрытие БЕЗ хардкода индекса среди уже существующих секций.
- `UFooter` осознанно оставлен ВНЕ цикла секций (рендерится всегда, если есть `settingsQuery.data`) — это шасси сайта, а не контентная секция, реордер/скрытие для него не имеет смысла.
- Протестировал реально: временно скрыл `services` (`visible: false`) и переставил `contacts` перед `hero` через прямой `curl PATCH` по `id` строк в `page_sections`, перезагрузил страницу — `services` пропал из DOM, `contacts` оказался раньше `symptoms`/`we-help` (проверено через `compareDocumentPosition`) — реордер и скрытие работают сквозным образом от Directus до рендера. Откатил оба изменения сразу после проверки (прод без staging).
- `pageSectionsQueryOptions` — единственный query-хук в проекте БЕЗ параметра `locale` (порядок/видимость секций не зависят от языка) — роут `/api/page-sections` без `?locale=`, но всё равно завёрнут в `localizeHref()` без явного `{ locale }`, как и внутренняя навигация (`footer.svelte`'s `localizeHref('/')`) — чтобы URL корректно резолвился под текущий активный `url`-strategy паралайда, а не потому что данные сами зависят от локали.

## Режим техобслуживания (2026-08-12)

- **Архитектурное напряжение, которое пришлось решить:** весь сайт — SSG, ВСЕ `/api/*`-роуты (включая `/api/settings`) были `export const prerender = true`, т.е. после деплоя на Vercel это статические JSON-файлы на CDN, а не серверлесс-функции. `hooks.server.ts` (сам это комментирует) вообще не выполняется для пререндеренных роутов на рантайме. Значит чистый серверный гейт в `hooks.server.ts` был бы no-op в проде — тумблер в Directus никогда бы не подхватился без пересборки+редеплоя всего сайта.
- Решение — **точечно** снял `prerender` только с `/api/settings/+server.ts` (`true → false`), не трогая пререндер остальных `/api/*` и страниц. Теперь этот один роут — обычная серверлесс-функция, всегда ходит в живой Directus. Все консьюмеры настроек (шапка, футер, hotline-баннер, контакты) от этого тоже выигрывают в свежести данных — не только maintenance mode.
- Плюс уменьшил `staleTime` именно у `settingsQueryOptions` до 60с (глобальный дефолт в `query-client.ts` — 10 мин, не трогал его — остальным секциям, у которых `/api/*` всё ещё пререндерен, частый рефетч всё равно не даст свежих данных, смысла нет). TanStack Query на клиенте видит, что гидрированные данные старше 60с (а после SSG-билда они гарантированно старше), и фонового рефетчит сразу после гидратации — именно так тумблер в Directus долетает до уже открытой у пользователя вкладки без хард-рефреша.
- **Честное ограничение, а не "решено полностью":** на самом первом пейнте (до гидратации и рефетча) статический HTML всё ещё может на долю секунды показать старую (пререндеренную на билде) версию сайта, даже если maintenance только что включили — SSG-природа сайта это не убирает. Полное исправление потребовало бы перевода всего сайта на SSR (`prerender = false` глобально) — сознательно НЕ стал делать это в одиночку: это меняет модель хостинга/производительности всего сайта, а не только one-off фичу, значит требует отдельного решения пользователя, а не побочный эффект одного пункта из `docs/need.md`.

Текст "сайт недоступен по техническим причинам" — НЕ в Directus, а в paraglide-сообщениях (`maintenance_title`/`maintenance_message`, `messages/ru.json`+`kk.json`) — по аналогии с `contacts_map_unavailable`: это статичный UI-текст ("технические работы"), а не редакторский контент, который меняется часто; тот же принцип, что уже применялся в проекте (лейблы кнопок/вкладок — paraglide, реальный контент клиники — Directus).

## Формы записи (DynamicForm) из Directus-схемы + hCaptcha (2026-08-13)

- Две отдельные Directus-коллекции (`booking_requests`, `sterilization_requests`), каждая — плоский список полей без условной видимости (сознательный выбор пользователя вместо одной формы с доп. полями при стерилизации — "проще поделить на две формы, тогда не придётся делать сложных условий"). Схема формы получается на лету через `readFieldsByCollection` (`getFormSchema()` в `directus.ts`) — редактор может добавлять/убирать поля прямо в Directus без правки кода фронтенда.
- Диспатч типа поля → Svelte-компонент — объект-таблица (`fieldRegistry` в `field-registry.ts`), НЕ if/else-цепочка (явное требование пользователя).
- `/api/forms/<collection>` (GET, схема) обязательно отдельный **статический** роут-файл на коллекцию, не `/api/forms/[collection]`: динамический сегмент, соседствующий с non-prerenderable `submit/+server.ts`, ломает `adapter-vercel`'ю сборку — вся статика для этого пути пропадает молча (без ошибки), см. также правило ниже про `prerender=true` + POST. Сабмит-роуты (`POST`) аналогично разнесены на `/api/forms/submit/<collection>/+server.ts` (не `/api/forms/<collection>/submit/`) — та же файловая коллизия директория/файл.
- `handleMissingId: 'ignore'` в `vite.config.ts`'s `prerender`-опциях обязателен, когда на сайте есть чисто клиентские hash-роуты (`#apply`, `#apply-sterilization` открывают Sheet через `page.url.hash`, не являются scroll-anchor'ами) — иначе prerender-краулер валит сборку с "no element with id=... exists", т.к. по умолчанию трактует любой `#fragment`-линк как ссылку на существующий на странице элемент.
- **Реальный, дважды-слойный баг Svelte 5** при `<FieldComponent bind:value={formData[field.field]} />`, где `formData` стартует как `{}`: до первого присваивания `formData[field.field]` — `undefined`, а это проходит через ДВА уровня `$bindable(...)`-с-фолбэком (сначала свой `value = $bindable('')` в `select-field.svelte`, потом ещё раз bits-ui `Select.Root`'а `value`) — Svelte 5 кидает `props_invalid_value: Cannot do bind:value={undefined} when value has a fallback value` и это ломает рендер ВСЕГО `{#each}`-блока (ни одно поле не рисуется, без явной ошибки в UI — только в консоли). Простое решение "проинициализировать ключ прямо в `{@const}`" (`{@const _ = formData[field.field] ??= ''}`) не работает — Svelte трактует мутацию `$state` внутри `{@const}`/template-выражения как derived-контекст и кидает `state_unsafe_mutation`. Рабочий фикс — сидировать ВСЕ ключи `formData` через `$effect.pre` при получении `schemaQuery.data`, **обязательно обернув чтение+запись `formData` в `untrack()`** — без этого сам эффект попадает в зависимость от `formData`, которую он же и пишет → `effect_update_depth_exceeded` (бесконечный цикл). Итоговый паттерн: `$effect.pre(() => { const fields = schemaQuery.data; if (!fields) return; untrack(() => { formData = seeded-from(fields, existing formData) }); })`. `svelte-autofixer` подсвечивает это как "malpractice"-подсказку (мутация `$state` внутри эффекта) — это ожидаемо и корректно для паттерна "сидировать локальное мутable-состояние из асинхронных query-данных", `$derived` тут не подходит, т.к. `formData` дальше мутируется пользовательским вводом через `bind:value`.
- **hCaptcha script-loading race**: `<script>.onload` стреляет, когда браузер закончил ЗАГРУЗКУ файла, но собственная асинхронная инициализация hCaptcha (доп. ресурсы/iframe) в этот момент ещё не готова — попытка `hcaptcha.render()` сразу после `script.onload` даёт консольный warning "should not render before js api is fully loaded" и ненадёжный рендер виджета. Правильный паттерн (по докам hCaptcha) — `?onload=<callbackName>&render=explicit` в URL скрипта + собственный `window.<callbackName>`, который hCaptcha вызывает САМА, когда реально готова; `<script>`'s `onload` не использовать вообще.
- Тестировал сквозной флоу вживую (прод-Directus, без staging): заполнил обе формы через реальный UI (`claude-in-chrome`, включая реальный select/чипы, БЕЗ решения самой hCaptcha — кликать/решать капчу automation-инструментом нельзя; т.к. `HCAPTCHA_SECRET_KEY` на сервере не задан (сознательная заглушка, см. ниже), `verifyCaptcha()` no-op'ится и пропускает сабмит без токена), проверил оба сабмита через прямой `GET /items/<collection>` в Directus, затем удалил обе тестовые записи (`DELETE /items/<collection>/:id`) — обычное для этого проекта "проверил на проде → откатил" в отсутствие staging.
- Ключ hCaptcha: `PUBLIC_HCAPTCHA_SITE_KEY` (клиентский, реальный, задан пользователем) в `.env`; `HCAPTCHA_SECRET_KEY` (серверный) сознательно НЕ задан — пользователь попросил заглушку ("ключи дам позже"), `verifyCaptcha()` возвращает `true` без обращения к hCaptcha API, если секрет не сконфигурирован — работает и для локальной разработки, и как временное состояние до реального продакшен-ключа.

- **Ширина `Sheet.Content` через `class` не переопределялась `sm:max-w-xl` "в лоб`.** Примитив (`sheet-content.svelte`) задаёт ширину через `data-[side=right]:sm:max-w-sm` — составной модификатор (data-атрибут + брейкпоинт). `cn()` (обёртка над `tailwind-merge`) дедуплицирует конфликтующие классы только когда у них СОВПАДАЕТ вся цепочка модификаторов — голый `sm:max-w-xl` (без `data-[side=right]:`) не распознаётся `tailwind-merge` как конфликт с `data-[side=right]:sm:max-w-sm`, оба класса остаются в разметке, и какой из них победит в реальном CSS — зависит от порядка сгенерированных правил в стилевом файле, а не от порядка в атрибуте `class`. На практике проигрывал override (ширина не менялась, измерено через `getBoundingClientRect()` — оставалось 384px вместо ожидаемых 576px). Фикс — повторить ТОТ ЖЕ модификатор в override: `data-[side=right]:sm:max-w-xl`. Общий урок: любой override ширины/позиционирования bits-ui/shadcn-примитива, чьи базовые классы сидят за `data-[state=...]`/`data-[side=...]`-вариантом, должен переопределяться с тем же вариантом-префиксом, иначе `tailwind-merge` его не сматчит и просто добавит вторым классом, который может проиграть по порядку в CSS.
- **2-колоночная адаптивная сетка полей — не своя система вёрстки, а переиспользование `field.meta.width` из самого Directus** (то самое поле, которое управляет раскладкой в админке: `full`/`half`/...). Добавлено в `FormFieldSchema.width` (`content.ts`) и `getFormSchema()` (`directus.ts`, `field.meta?.width === 'full' ? 'full' : 'half'`). `dynamic-form.svelte` оборачивает `{#each}` в `grid grid-cols-1 sm:grid-cols-2 gap-4`, каждое поле — в `<div class={field.width === 'full' ? 'sm:col-span-2' : ''}>`. Проставлены ширины на обеих коллекциях (`service`/`pet_type`/`pet_type_other`/`name`/`phone`/`preferred_date`/`pet_sex` → `half`, `reason` — как многострочный текст — остаётся `full`). Тот же принцип "не изобретать вторую систему разметки, когда Directus уже её хранит", что и раньше в проекте для `list-o2m` sort/шаблонов.
- **`preferred_date`: string+`input` → нативный Directus `dateTime`+`datetime`, рендерится как `<input type="datetime-local">` через `UInput`** (bits-ui `DatePicker` не выбирает время — пользователь сам это отметил, поэтому взят нативный HTML-контрол вместо смешивания двух виджетов под один field). Новый компонент `fields/datetime-field.svelte`, зарегистрирован в `field-registry.ts` под ключом `datetime` (Directus `meta.interface` для `dateTime`-полей называется именно так).
  - **Реальный баг миграции схемы**: `PATCH /fields/:collection/:field` с одним `{"type":"dateTime"}` (или даже вместе с `meta`) отвечает 200 и ЭХОМ возвращает `"type":"dateTime"` в some случаях, но при повторном `GET` поле остаётся старым (`type: "string"`, `data_type: "character varying"`) — Directus принимает запрос, но не запускает ALTER COLUMN, если в теле нет явного `schema.data_type`. Рабочий payload: `{"type":"dateTime","schema":{"data_type":"timestamp without time zone"}}` — только тогда колонка реально мигрирует (проверено `GET`-перечитыванием после каждой попытки, как требует `directus`-skill). `timestamp without time zone` — правильный тип именно для редактируемого пользователем `dateTime`-поля (в отличие от `timestamp with time zone`, который Directus использует для системных `date-created`/`date-updated`-полей вроде уже существующего `date_created`).
- В Directus убраны "Аптека"/"Зоомагазин" из choices поля `service` (`booking_requests`) — эти пункты не подходят для формы записи на приём (были в исходном сиде "на всякий случай", пользователь явно попросил убрать).

### Реальный баг: анимация sheet записи не работала вообще (не только "pop" полей) + тёмный фон для всех sheet (2026-08-13)

- Предыдущая запись (выше) объяснила асимметрию между бургер-меню и `booking-sheet.svelte` только "pop"-эффектом полей формы — это было ЧАСТЬЮ правды, но пользователь сообщил "анимация у записаться не работает" уже из реального браузера, что указывало на нечто более фундаментальное. **Реальный корень**: `booking-sheet.svelte` оборачивал ВЕСЬ `<Sheet.Root>` в `{#if activeForm}` и передавал `open={true}` литералом. При каждом открытии (смене hash на `#apply`) весь Sheet.Root+Content монтировался ЗАНОВО, уже с `open=true` на самом первом рендере — Svelte не видит перехода `false→true` для `{#if open}`-блока внутри `SheetPrimitive.Content`'s child-сниппета, потому что блок был `true` с самого начала своего существования, а `transition:`-директивы играют только на реактивном переключении состояния у УЖЕ смонтированного дерева, не на "родился сразу таким". У бургер-меню (`nav-menu.svelte`) `<Sheet.Root bind:open>` смонтирован ОДИН раз при загрузке страницы с `open=false`, и клик по триггеру реально переключает `false→true` у живого дерева — отсюда и работающая анимация именно там.
  - **Фикс**: убрал внешний `{#if activeForm}` полностью, `Sheet.Root` теперь смонтирован всегда; `open` стал `$derived(activeForm !== undefined)` — реактивное булево, а не литерал, передаётся в `open={open}` (не `bind:open`, т.к. закрытие всё ещё идёт через `onOpenChange` → `goto()` для очистки hash, а не через двустороннюю привязку). Переключение содержимого (booking vs sterilization форма) осталось на `{#if activeForm === 'booking_requests'}{:else if ...}{/if}` ВНУТРИ `Sheet.Content` (третья ветка — просто ничего не рендерить, когда `activeForm` `undefined`, а не молчаливый fallback на форму стерилизации, как было раньше по ошибке в старой `{:else}`-ветке).
  - **Как проверял, не имея возможности напрямую смотреть на движение в этом окружении** (см. ранее задокументированный `document.hidden`-артефакт): сравнил ОДИНАКОВЫЙ тест (замер `getComputedStyle(...).transform` сразу после клика и через 20/60/120/250мс) на бургер-меню (заведомо рабочем) и на sheet записи. ОБА показали идентичный симптом — `transform` застревает на СТАРТОВОЙ офф-скрин позиции (`translateX(100%)`, то есть `matrix(1,0,0,1,<ширина>,0)`) и не прогрессирует ни на одном из двух — это ЕДИНООБРАЗНОЕ поведение с уже известным (задокументированным ранее) артефактом compositor'а при `document.hidden: true`, а не разница между «работает»/«не работает». Ключевой диагностический сигнал — САМ ФАКТ, что после фикса transform на первом кадре равен стартовому офф-скрин смещению (а не `none`/`matrix(1,0,0,1,0,0)`, как было бы, если бы Svelte по-прежнему пропускал transition при монтировании) — это подтверждает, что Svelte теперь ДЕЙСТВИТЕЛЬНО распознаёт вход как анимируемый переход, просто дальнейшую интерполяцию в этом окружении не видно.
  - Отдельная грабля при автоматизированной проверке: клики по бургер-кнопке через `computer`-инструмент с пиксельными координатами, снятыми со скриншота, промахивались мимо реального элемента — `getBoundingClientRect()` показал, что фактический CSS-viewport шире, чем то, что подразумевал масштаб скриншота (кнопка была на x≈1494–1558, а клик шёл на x=1376). Правильный способ клика в таких случаях — `document.querySelector(...).click()` через `javascript_tool`, а не координаты с скриншота, если есть малейшее сомнение в масштабе.
- **Тёмный фон `--color-brand-ink` для ВСЕХ Sheet** (бургер-меню и обе формы записи, по явному запросу пользователя) — так как токен объявлен в `:root`, но не проброшен в `@theme inline` (тот же паттерн, что и `--color-warning-bg`/`--color-brand-primary-dark` ранее), применён через `bg-[color:var(--color-brand-ink)]` в общем примитиве `sheet-content.svelte`, вместе с `text-white` вместо `bg-popover text-popover-foreground`. Это КАСКАДНО изменило контекст: всё, что раньше полагалось на наследование `text-foreground` от белого/кремового фона (`body { @apply text-foreground }`, тёмно-чернильный), должно было либо (а) явно перейти на `text-white`, либо (б) явно закрепить СВОЙ тёмный текст, если у элемента есть собственная СВЕТЛАЯ поверхность внутри тёмного sheet (инпуты, select-триггер).
  - (а) Явный `text-white`: заголовок/текст успеха в `dynamic-form.svelte`, лейблы (`ULabel`) во всех 5 field-компонентах (`form-field.svelte`, `textarea-field.svelte`, `select-field.svelte`, `chip-group-field.svelte`, `datetime-field.svelte`), `PhoneLink` и неактивная вкладка `LocaleSwitch` (variant `tab`, используется только в бургер-меню — variant `pill` в шапке не тронут, там свой светлый фон).
  - (б) Явный тёмный текст на своей светлой поверхности: `UInput`/`UTextarea` (`ui/input/input.svelte`, `ui/textarea/textarea.svelte`) не имели ВООБЩЕ никакого явного цвета текста — держались на унаследованном (раньше тёмном, значит совпадало с белым фоном инпута случайно). Добавлен explicit `text-foreground` в БАЗОВЫЙ класс обоих примитивов — это исправление глобальное (влияет на все инпуты по сайту, не только в тёмных sheet), но строго корректное: инпут с непрозрачным белым фоном не должен полагаться на цвет текста от родителя. Аналогично — `Select.Trigger` в `select-field.svelte` получил explicit `text-foreground` (у самого bits-ui `select-trigger.svelte` тоже нет своего цвета текста).
  - Что НЕ трогал осознанно: чипы (`chip-group-field.svelte`, активная/неактивная — `bg-primary text-primary-foreground`/`bg-secondary text-secondary-foreground`), порталящийся `Select.Content` (свой `bg-popover text-popover-foreground`, рендерится вне DOM-поддерева sheet через портал — не наследует), `Alert.Root variant="warning"` (свой светлый `bg-[var(--color-warning-bg)]`, дочерний `Alert.Description`'s `text-muted-foreground` сидит НА этом светлом фоне алерта, а не на тёмном фоне sheet) — все эти элементы самодостаточны по цвету и не зависят от фона-контейнера.
- **Растяжка на весь экран на мобильных** — в `sheet-content.svelte` `data-[side=left]:w-3/4`/`data-[side=right]:w-3/4` заменены на `w-full` (без брейкпоинт-префикса, значит действует по умолчанию, т.е. на мобильных); существующий `data-[side=*]:sm:max-w-sm`/`sm:max-w-xl` по-прежнему ограничивает ширину только от `sm:` (640px) и выше — итог: sheet на телефоне занимает весь экран, на десктопе — прежняя капированная ширина.

## Available Svelte MCP Tools:

### 1. list-sections

Use this FIRST to discover all available documentation sections. Returns a structured list with titles, use_cases, and paths.
When asked about Svelte or SvelteKit topics, ALWAYS use this tool at the start of the chat to find relevant sections.

### 2. get-documentation

Retrieves full documentation content for specific sections. Accepts single or multiple sections.
After calling the list-sections tool, you MUST analyze the returned documentation sections (especially the use_cases field) and then use the get-documentation tool to fetch ALL documentation sections that are relevant for the user's task.

### 3. svelte-autofixer

Analyzes Svelte code and returns issues and suggestions.
You MUST use this tool whenever writing Svelte code before sending it to the user. Keep calling it until no issues or suggestions are returned.

### 4. playground-link

Generates a Svelte Playground link with the provided code.
After completing the code, ask the user if they want a playground link. Only call this tool after user confirmation and NEVER if code was written to files in their project.
