# Как переносить схему между клиентами

См. [README.md](README.md) для карты остальных файлов. Что именно переносится — в [architecture.md](architecture.md).

## Механика — `schema snapshot`/`apply`

Директус уже даёт портируемый механизм, без своих полей и плагинов:

- `directus schema snapshot -y schema.yaml` — снимок структуры (коллекции, поля, relations), **не** контент. Хранится в git как обычный YAML/JSON-файл шаблона.
- `directus schema apply schema.yaml` — накатывается на чистый Directus-инстанс нового клиента.
- Новый клиент = чистый Directus-инстанс + `schema apply` **core** (см. [architecture.md](architecture.md)) + только нужных ему типов из библиотеки блоков/пунктов меню + отдельный деплой SvelteKit-приложения (тот же код, что и у остальных клиентов — компоненты и `block-registry` живут в общем пакете/шаблоне-репозитории, не копипастятся вручную).
- Тип блока, добавленный ради одного клиента, попадает в общую библиотеку только осознанно — через promotion gate скилла `site-blueprint` (`.claude/skills/site-blueprint/SKILL.md`), не автоматически.

Это отвечает на исходный вопрос «нельзя ли шаблонировать без своих полей/плагинов»: можно — `schema apply` и есть шаблонирование, но применённое к generic core+библиотека-типов модели, а не к сегодняшней bespoke-модели одного сайта (там каждый клиент с другим набором секций тут же требует правки enum'а и кода).

## Открытые архитектурные вопросы (решение за пользователем)

- **Один Directus-инстанс на клиента vs. multi-tenant** (общий инстанс, у коллекций — поле `site_id`). Дефолт здесь — **отдельный инстанс на клиента**: проще биллинг/изоляция/права доступа сотрудников клиники. Multi-tenant экономит инфраструктуру, но усложняет права доступа и schema-миграции (нельзя накатить breaking-change на общую схему без синхронного даунтайма всех клиентов) — стоит выбирать только если счёт пойдёт на десятки+ сайтов.
- **Общий npm-пакет Svelte-компонентов** (`block-registry`/`nav-registry` + сами блоки) между репозиториями клиентов, или каждый клиент — форк шаблон-репозитория. Пакет чище (один источник правды, баг чинится один раз), форк проще для разовой кастомизации одного клиента без риска сломать остальных. Не решено — имеет смысл выбрать после 2-3 реальных клиентов.

Вопрос «кто решает, что тип блока достоин попасть в общую библиотеку» закрыт отдельно — это и есть скилл `site-blueprint` (см. [why-not-one-schema.md](why-not-one-schema.md)), не открытый вопрос.
